# Job Scraper

---

## How It Works

Этот skill ищет вакансии через **установленные portal-search CLI** в
`.agents/skills/` (плюс WebSearch как фолбэк), используя запросы из профиля.
Он дедуплицирует против уже виденных вакансий и трекера заявок, и
представляет новые совпадения с быстрой оценкой соответствия.

## Invocation

Пользователь запускает этот skill фразами вроде:
- "Найди новые вакансии"
- "Поищи вакансии"
- "Есть новые позиции?"
- "/scrape"

Опциональные аргументы:
- Фокус-область, например "/scrape data science" или "/scrape geophysics"
- "broad" для запуска всех категорий поиска, например "/scrape broad"
- "health" для запуска только проверки здоровья порталов (Step 4.75), без поиска, дедупликации или показа вакансий - например "/scrape health", или "/scrape health <portal-name>", чтобы проверить один портал по имени (работает, даже если у этого портала `enabled: false`)

## Execution Steps

### Step 0: Load State

1. Прочитать `job_scraper/seen_jobs.json` (создать, если отсутствует - начать с `{"seen": {}}`)
2. Прочитать `job_search_tracker.csv`, чтобы извлечь компании+роли, по которым уже был отклик
3. Прочитать `search-queries.md` (эта директория) для шаблонов категорий запросов (ключевые слова, порядок приоритета, языковой охват) - они живут только здесь, в `source.md` нет терминов запросов.
4. **Прочитать актуальный список площадок из Obsidian** (добавлено 17-09-2026): `vault_read` по `01-PROJECTS/поиск-работы/source.md`. Это единственное место, где пользователь редактирует, на какие площадки нацеливаться - собственный раздел "Search Sites" в `search-queries.md` - это снимок на момент времени для читаемости, а не второй источник истины. Если `source.md` перечисляет площадку, не упомянутую в `search-queries.md`, всё равно использовать её с общими запросами `site:`, построенными из ключевых слов категорий; если площадка из `search-queries.md` больше не в `source.md`, отбросить её для этого прогона. Если инструменты Obsidian MCP недоступны, откатиться к статичному списку из `search-queries.md` и сказать об этом в отчёте Step 5.

### Step 1: Search

Прочитать `search-queries.md` (эта директория) для стратегии поиска. По умолчанию запускать топ-3 категории запросов по приоритету. Если пользователь сказал "broad" - запускать все категории. Если пользователь указал фокус-область (например, "data science") - приоритизировать запросы из этой категории.

**Использовать установленные CLI-инструменты как основной механизм поиска.** Откатываться на `WebSearch` только для порталов без CLI-скилла или если `bun` недоступен в системе.

#### 1a. Check bun availability

```bash
bun --version
```

Если это падает (bun не установлен), перейти сразу к **1c (WebSearch fallback)** для всех порталов и отметить фолбэк в выводе Step 5.

#### 1b. Run CLI tools (primary — run these in parallel where possible)

Обнаружить все установленные portal CLI skill'ы, прочитав каждый `SKILL.md` под `.agents/skills/*/SKILL.md`. Каждый файл документирует точные CLI-флаги этого портала и примеры использования. **Использовать собственный документированный интерфейс каждого портала — не угадывать флаги.** Такой подход автоматически включает любые новые порталы, добавленные через `/add-portal`, без изменений в этом файле.

**Соблюдать переключатель `enabled`.** Портал включён, если только его frontmatter в `SKILL.md` не задаёт `enabled: false` (отсутствующий ключ означает включено — это значение по умолчанию). Пропускать каждый выключенный портал и фиксировать его для сводки Step 5. Так форк может держать портал установленным, но пропускать его в прогоне, не удаляя его директорию.

Для каждого **включённого** portal skill:

1. Прочитать его `SKILL.md`, чтобы найти правильный вызов `bun run …` и поддерживаемые флаги.
2. Перевести термины запроса из `search-queries.md` в формат флагов этого портала (например, `--key`, `--search-string`, `--query`, коды фильтров — что бы ни указывал SKILL.md портала).
3. Ограничить последними 14 днями через поддерживаемый порталом флаг **фильтра** свежести (`--jobage`, `--since <YYYY-MM-DD>` и т.д. — как задокументировано для конкретного портала; `hh-search`, `linkedin-search` и `freehire-search` все поддерживают `--jobage`). Портал **без флага свежести** всё равно должен быть ограничен: вывод поиска каждого портала несёт поле `date`, поэтому фильтровать на стороне клиента — отбрасывать результаты с `date` старше 14 дней после возврата вызова, и никогда не выдумывать флаг, не задокументированный SKILL.md портала (CLI отклоняют неизвестные флаги). Флаг сортировки (например, `--order PublicationDate`) - это сортировка, а сортировка - не фильтр — сочетание его с `--limit` является допустимым приближением на портале, который не предлагает ничего лучше, но клиентский фильтр по дате всё равно применять сверху. Это особенно важно для будущего skill'а, сгенерированного через `/add-portal`, который вообще не поставляется с флагом свежести.
4. Ограничить результаты ~20 на вызов через флаг лимита портала.
5. Использовать `--format json` для машиночитаемого вывода.

Запускать все вызовы portal CLI параллельно, где возможно, через инструмент Agent. Собрать все массивы `results` в единый пул для Step 2, сохраняя за каждым результатом тег его портала-источника (для Step 2 `detail`-запросов).

Если CLI-инструмент завершается с ненулевым кодом, залогировать сообщение об ошибке и продолжить — не прерывать весь поиск целиком.

#### 1c. WebSearch fallback

Использовать `WebSearch` для:
- Порталов, перечисленных в `search-queries.md`, у которых **нет** соответствующей директории под `.agents/skills/`
- Любого портала, чей CLI падает во время выполнения
- Когда bun недоступен (Step 1a провалился)

Использовать строки запросов конкретных площадок из `search-queries.md` напрямую как запросы WebSearch для этих порталов.

Помечать каждый fallback-результат как полученный через WebSearch, сохраняя тег портала, когда фолбэк подменяет установленный портал, чей CLI упал. Step 4 сохраняет это как поле `source` записи, а Step 5 сообщает, какие порталы работали через фолбэк в этом прогоне.

### Step 2: Fetch & Parse

Для каждого перспективного результата из Step 1:

**Из результатов CLI:** вывод поиска уже включает title, company, location, date
и URL. Для вакансий, заслуживающих более глубокого рассмотрения, загрузить полную
детализацию через команду `detail` этого портала (см. его SKILL.md — не угадывать
флаги), чтобы извлечь **ключевые требования**, **дедлайн подачи** и короткий
сниппет описания.

**Обнаружение закрытых на источнике:** `linkedin-search detail` также возвращает
`isActive`. `false` означает, что сама страница вакансии рендерит баннер LinkedIn
"No longer accepting applications" — вакансия умерла между индексацией и загрузкой
(истёкшие URL LinkedIn редиректят на *похожие живые вакансии*, поэтому попадание в
поиске может оказаться призраком). Помечать такую вакансию, никогда не отбрасывать
молча: записать её в `seen_jobs.json` в Step 4 с `"status": "expired"` и не включать
в презентацию Step 5 — отсутствующая запись выглядит идентично никогда не виденной
вакансии, а зафиксированный статус - это то, что делает будущий отчёт о призраках
самодиагностируемым. `isActive: true` - это лишь отсутствие этого баннера, не
доказательство, что вакансия открыта; дедлайны и мёртвые URL остаются задачей `/rank`.

**Из результатов WebSearch:** использовать `WebFetch` по URL вакансии и извлечь те же
поля вручную. При HTTP 403 повторить с браузерными заголовками через curl по
`.claude/skills/job-application-assistant/09-web-research.md`, прежде чем сдаться — большинство
банковских и корпоративных сайтов отклоняют user-agent WebFetch, при этом нормально
отдавая страницу браузерам.

**Сохранять URL, который реально ведёт на саму вакансию.** URL страницы-листинга с
добавленным `#fragment` (`.../jobs/ciso/#ikerian`) - это не вакансия: он успешно
загружается и возвращает несвязанные названия вакансий, из-за чего каждый последующий
прогон `/rank` и `/apply` будет проваливаться на этой записи. Если WebSearch выдаёт
только страницу листинга, искать роль на карьерном сайте самого работодателя и
сохранить этот URL вместо неё, либо отбросить кандидата, а не сохранять ссылку с
фрагментом.

Для каждого кандидата:
- Пропустить, если URL совпадает с любой существующей записью в `seen_jobs.json`,
  независимо от ключа этой записи. Это сохраняет непрерывность дедупликации для
  вакансий, сохранённых по правилу ключа до появления helper'а, пока новые записи
  используют канонический ключ из Step 4.
- Иначе пропустить, если комбинация компания+название уже есть в `seen_jobs.json`
- Пропустить, если компания+роль уже фигурирует в `job_search_tracker.csv`

### Step 2.5: Mass-Posting Detection (within this run)

Паттерн распространения, который стоит пометить пользователю как сигнал для
осторожности, а не как обвинение в адрес работодателя - он описывает то, как
листинг распространяется, а не вердикт о легитимности компании. Сам по себе он
ничего не доказывает (компании законно нанимают на одну и ту же роль в нескольких
городах); пометить его, чтобы пользователь мог учесть это при решении, стоит ли
тратить время, не понижать соответствие и не исключать результат молча из-за этого.

Если два или более результата в пуле этого прогона (от одной компании, или с одним
и тем же req/job ID, видимым в URL или названии) имеют по сути одинаковое описание
и отличаются только городом/локацией/названием, не представлять их как отдельные
строки. Объединить в одну строку и отметить разброс, например "опубликована
идентично в 6 городах (BR, MX, GT)".

### Step 3: Quick Fit Assessment

Для каждой новой вакансии сделать быструю проверку соответствия (НЕ полную оценку
из `04-job-evaluation.md` - только быстрый сигнал):

- **High match**: роль напрямую задействует ключевые навыки кандидата
- **Medium match**: роль смежна с опытом кандидата
- **Low match**: роль требует значительных навыков, которых у кандидата нет

**Language override:** перед присвоением уровня совпадения проверить вакансию против
Language Gate из `04-job-evaluation.md` (требуемый язык, вообще не заявленный в
таблице Languages в CLAUDE.md). Полностью незаявленный требуемый язык переопределяет
соответствие по навыкам: пометить как **Low** независимо от того, насколько хорошо
совпадают навыки, и назвать это в пунктах-акцентах, чтобы это не затерялось под
внешне хорошим совпадением. **Заявленный** язык с требованием, читающимся выше
заявленного уровня, - это *не* переопределение — оценивать соответствие как обычно,
но добавить red-flag пункт под акцентами этой вакансии (Step 5), процитировав
требование вакансии рядом с заявленным уровнем, чтобы разрыв был виден без
автоматического понижения.

### Step 4: Deduplicate & Store

1. Выводить ключ каждой записи через helper, никогда не слагифицировать на месте:

```bash
python3 tools/job_key.py --company "<company>" --title "<title>" --url "<url>"
```

Он печатает одну строку: канонический ключ для этой вакансии. Ключ должен быть чистой функцией от вакансии, потому что два прогона, слагифицирующие по-разному, сохранят одну и ту же вакансию дважды и сведут на нет дедупликацию, ради которой существует этот шаг. Helper также ограничивает длину длинных названий и разрешает неоднозначность обрезки хэшем от полного slug, поэтому обрезанное название стабильно между прогонами, а два разных длинных названия никогда не столкнутся. `python3 tools/job_key.py --audit` сообщает о записях в существующем файле состояния, которые предшествуют этому правилу; он только сообщает и никогда не переписывает ключи, поскольку переписанный ключ ломает собственное сопоставление компания+роль в трекере.

2. Добавить ВСЕ загруженные вакансии (новые и пропущенные) в `seen_jobs.json` со структурой:
```json
{
  "seen": {
    "<key from tools/job_key.py>": {
      "title": "...",
      "company": "...",
      "url": "...",
      "first_seen": "YYYY-MM-DD",
      "posted_date": "YYYY-MM-DD" | null,
      "deadline": "YYYY-MM-DD" | null,
      "fit": "high/medium/low",
      "status": "new/skipped/ranked/expired",
      "portal": "<source portal skill, e.g. hh-search>",
      "source": "cli/websearch"
    }
  }
}
```

Поле `portal` фиксирует, какой CLI skill произвёл вакансию (результаты уже помечены тегом портала в Step 1b - сохранить этот тег здесь). Записи, написанные до появления этого поля, его не имеют; проверка здоровья (Step 4.75) атрибутирует их, сопоставляя домен URL с базовым URL каждого портала, поэтому не бэкфиллить.

Поле `source` фиксирует, какой механизм произвёл запись: `cli` для вывода portal-CLI из Step 1b, `websearch` для фолбэка Step 1c. Именно это делает отчёт о вакансиях-призраках диагностируемым после того, как сводка прогона исчезла: сохранённая запись, чей URL позже ведёт в никуда (или на другую вакансию), читается совсем по-разному в зависимости от того, пришла ли она из живого вывода CLI или из поискового индекса, который может отставать на недели - а показанная вакансия вообще без записи здесь указывает на выдумывание, что запрещено правилом 1. Записи, написанные до появления этого поля, его не имеют; никогда не бэкфиллить его - механизм не был зафиксирован.

`/rank` расширяет эту схему аддитивно: ранжированные записи также несут `rank_score` (общий балл 0–100), `rank_verdict` (полоса соответствия, например "strong fit"), `rank_date` (дата ранжирования в ISO), поля вето `location_verdict` и `language_gate` (оба PASS/FAIL/FLAG) с `language_note` (процитированное требование, объясняющее не-PASS), и `strengths`/`gaps` (по 1-3 дословных пункта каждый, скопированных из находок оценивающего агента). Поле `status` устанавливается в `"ranked"`. Не удалять ни одно из этих полей при перезаписи записей. Записи, ранжированные до появления `strengths`/`gaps`, просто их не имеют; читающие терпимо относятся к их отсутствию и никогда не бэкфиллят угадыванием. Записи, ранжированные до переименования вердикта, могут нести устаревшую строку PASS/FAIL/FLAG в `location` - читать это как вердикт, когда `location_verdict` отсутствует; в свежих записях `location` - это всегда место, никогда не вердикт.

`deadline` - это базовое поле, а не расширение `/rank`: загрузка детализации в Step 2 уже извлекает дедлайн подачи, поэтому он записывается при первом обнаружении вакансии и обновляется в Step 4 команды `/rank`, когда оценивающий агент возвращает другое значение. `null` означает, что вакансия не указывает дедлайн; отсутствующий ключ означает, что запись предшествует этому полю - **никогда не выводить дедлайн** ни из того, ни из другого, и никогда не бэкфиллить угадыванием.

`posted_date` - это собственная дата публикации вакансии, взятая из поля `date`, которое контракт Step 2 уже гарантирует в выводе поиска каждого portal CLI. Step 1b использует эту дату, чтобы ограничить прогон последними 14 днями, а затем отбрасывает её, так что ничто дальше по пайплайну не может отличить вакансию, опубликованную вчера, от опубликованной два года назад - `first_seen` - это когда скрапер впервые увидел запись, а не когда работодатель её опубликовал. Сохранение этого поля делает окно Step 1b проверяемым после прогона и даёт `/rank` сигнал свежести для учёта, вместо того чтобы заново вычислять дату и записывать её в прозе, которую никто не читает. Этот пробел проявился реально: вакансия freehire-search с датой 2024-05-13 была спарсена и ранжирована как Strong Fit на позиции 1 из 133, при этом собственная заметка оценки отметила, что листинг "может быть давно устаревшим", но ничто не могло на это отреагировать. `null` означает, что портал не вернул дату для этого результата (CLI выдают `date: null`, когда листинг её опускает); отсутствующий ключ означает, что запись предшествует этому полю - **никогда не выводить дату публикации** ни из того, ни из другого, и никогда не бэкфиллить угадыванием.

3. Показывать только вакансии, которых ЕЩЁ НЕТ в списке виденных (по совпадению
   URL или компания+название) или в трекере.

### Step 4.5: Generate Referral Contact Links (High & Medium Fit Only)

Для каждой вакансии из этого прогона с `fit` **high** или **medium** (пропускать
low-fit вакансии) построить два URL поиска людей в LinkedIn, чтобы пользователь мог
найти рекрутёра или участника команды для запроса referral или тёплого знакомства.
Это намеренно шаг генерации ссылок, а не автоматизированный поиск: без скрапинга,
без стороннего API, без зависимостей времени выполнения или учётных данных.

**A. Recruiters / Talent Acquisition (the referral path)**
```
https://www.linkedin.com/search/results/people/?keywords=<url-encoded "<Company Name> recruiter">&origin=GLOBAL_SEARCH_HEADER
```

**B. Role/team peers (informational-outreach / warm-intro path)**
```
https://www.linkedin.com/search/results/people/?keywords=<url-encoded "<Company Name> <role keyword>">&origin=GLOBAL_SEARCH_HEADER
```
Использовать короткое ключевое слово из названия вакансии для `<role keyword>` -
например, вакансия с названием "AI Program Manager" становится
`"<Company Name> AI Program Manager"`.

Обе ссылки предназначены для того, чтобы пользователь открыл их и просматривал сам -
никогда не загружать и не скрапить страницы результатов поиска людей LinkedIn
программно. Никогда не выдумывать контакты и не заявлять, что найден конкретный
человек; это ссылки на поиск, а не результаты.

### Step 4.6: Sync New Vacancies to Obsidian `Вакансии.md`

Для каждой вакансии в пуле этого прогона (все уровни fit - в отличие от Step 4.5, здесь нет ограничения high/medium) синхронизировать её с таблицей Obsidian по `01-PROJECTS/поиск-работы/Вакансии.md`, чтобы ручной дашборд пользователя оставался актуальным без повторной вставки ссылок вручную.

1. **Прочитать текущую таблицу.** `vault_read` файла с `targetType: "heading"`, `target: ["Вакансии"]`, `scope: "content"`. Убедиться, что последний блок тела - это таблица (так и должно быть - вступительный абзац, легенда "Статусы:", затем таблица). Если форма файла изменилась и таблица больше не последний блок, остановиться и сказать пользователю, а не угадывать, какой блок редактировать.

2. **Дедуплицировать против существующей таблицы**, а не только против `seen_jobs.json`: собрать множество URL, уже присутствующих в колонке "Вакансия" таблицы (любая строка, любой статус). Пропустить вакансию из этого прогона, если её URL уже в этом множестве - это покрывает и "уже залогирована", и "уже залогирована и отклонена" одной проверкой, поскольку отклонённая строка - всё равно строка в таблице.

3. **Также истекать устаревшие строки**, раз уж таблица всё равно перестраивается: разобрать "Дата добавления" каждой существующей строки (формат `DD.MM.YYYY` - совпадает с существующими строками в файле vault, а не с ISO-форматом, используемым в остальной части этого репозитория); строка, чья дата более чем на 30 дней раньше сегодняшней, отбрасывается **независимо от её Статуса** (заявка в процессе старше 30 дней тоже отбрасывается - это осознанный, слегка агрессивный дефолт, выбранный пользователем; отметить это пользователю один раз, если видно, что это реально удаляет строку с непустым статусом, чтобы он мог сузить правило позже, если это его удивит). Строки вообще без даты (добавленные до появления этой автоматизации, или добавленные вручную без неё) оставляются как есть - никогда не угадывать и не бэкфиллить дату, и никогда не отбрасывать строку без даты.

4. **Перестроить блок таблицы:** строка заголовка, строка-разделитель, затем уцелевшие старые строки (после фильтра истечения), за которыми следует по одной новой строке на каждую уцелевшую новую вакансию из этого прогона - `Дата добавления` = сегодняшняя дата (`DD.MM.YYYY`), `Вакансия` = URL вакансии, все остальные колонки пустые. Сохранять точный порядок колонок и стиль отступов, уже принятый в файле.

5. **Записать обратно одним точечным патчем**, никогда не перезаписью всего файла: `vault_patch` с `targetType: "heading"`, `target: ["Вакансии"]`, `within: -1` (таблица - последний блок тела), `operation: "replace"`, `scope: "content"`, `content` = вся перестроенная таблица как буквальный markdown. Это затрагивает только блок таблицы - вступительный абзац и легенда Статусы над ним не трогаются.

6. **Отчитаться об этом в сводке Step 5**, одной строкой: сколько новых строк добавлено и сколько устаревших строк истекло (например, `Вакансии.md: +7 new, 2 expired (>30d)`). Опускать строку только если оба счётчика равны нулю.

Если инструменты Obsidian MCP недоступны в этой сессии по любой причине, пропустить этот шаг и явно сказать об этом в выводе Step 5 - никогда не проваливать весь прогон `/scrape` из-за этого, и никогда не угадывать содержимое файла без предварительного чтения.

### Step 4.75: Portal Health Check

CLI на базе скрапинга портят молча: когда портал меняет разметку, парсер обычно
выходит с кодом 0 с нулём результатов или с null/искажёнными полями, а фолбэк
Step 1c никогда не срабатывает, потому что он триггерится только на жёсткий сбой.
Этот шаг ловит это по уликам, которые прогон уже несёт в себе.

**Бесплатная проверка (без дополнительных запросов).** Для каждого включённого портала, который отработал в Step 1b:

- **Degraded scan:** осмотреть результаты, которые он вернул в этом прогоне. Флаги: `company` null или пусто во всех результатах, пустые названия, неразэкранированные сущности (`&amp;`) или HTML-фрагменты в названиях, URL, не ведущие на портал. Любое из этого означает, что парсер работает наполовину, а `/scrape` молча собирает мусор.
- **Yield history:** если портал вернул ноль результатов по всем запросам этого прогона, проверить, содержит ли `seen_jobs.json` прежние записи от него (через поле `portal`, или сопоставлением доменов URL для записей, предшествующих этому полю). Портал, дававший вакансии на прошлых прогонах и не дающий ничего сейчас, подозрителен - те же запросы работали раньше.

**Эскалация (ограниченная, только при подозрении).** Подозрительный портал получает **один** контрольный пробный запрос: запустить его документированный `search` с примером запроса из его собственного SKILL.md (этот запрос доказанно работал на момент регистрации skill'а), флаг лимита портала, ограниченный до 3, `--format json`. Если это ничего не возвращает, повторить **один раз** с одним распространённым словом. Только тогда вердикт - **broken**. 429 или страница блокировки **никогда** не являются доказательством поломки - записать портал как **inconclusive (rate-limited)**, отступить и не повторять.

**Verdicts.** Здоровые порталы получают тишину - ни таблицы, ни строки. Всё остальное всплывает в сводке Step 5 как строка здоровья.

**Probe-only mode (`/scrape health`).** Пропустить Steps 1-4 и бесплатную проверку этого шага (нет свежего прогона для сканирования); вместо этого пробовать каждый установленный портал напрямую - включённые по умолчанию, выключенный только когда назван явно (например, `/scrape health <portal-name>`). Каждый портал получает контрольный пробный запрос выше, критерии degraded применяются к тому, что он вернул, и - поскольку пользователь явно попросил диагностику - одна загрузка `detail` на первом результате каждого здорового портала (описание должно быть читаемым разэкранированным текстом; сбой понижает статус до degraded). В этом режиме отчитываться обо всех статусах, включая здоровые. Объём остаётся ограниченным: один поиск, максимум один повтор, максимум одна `detail`-загрузка на портал.

## Important Rules

1. **Никогда не выдумывать вакансии.** Показывать только вакансии из реального вывода CLI search/detail или результатов WebSearch/WebFetch.
2. **Соблюдать дедупликацию.** Всегда проверять seen_jobs.json И job_search_tracker.csv перед показом.
3. **Фокус на настроенной географической области.** Пропускать вакансии, требующие релокации или явно вне диапазона поездок.
4. **Только открытые позиции.** Пропускать вакансии с истёкшими дедлайнами или помеченные как закрытые.
5. **Эффективно расходовать загрузки детализации.** Не запускать `detail` или WebFetch на каждом попадании поиска — сначала отфильтровать по названию/сниппету, затем загружать только перспективные совпадения.
6. **Параллельные поиски.** Запускать поиски portal CLI параллельно; использовать WebSearch только для пробелов, которые CLI не покрывают.
7. **Никаких автоматизированных поисков людей.** Контакты для referral (Step 4.5) - это только ссылки поиска LinkedIn - никогда не загружать и не скрапить страницы результатов поиска людей LinkedIn программно.
8. **Проверки здоровья ограничены и честны.** Step 4.75 тратит максимум один пробный запрос, один повтор и (в режиме `health`) одну загрузку detail на портал - это диагностика, а не обход. Rate-limit никогда не является доказательством поломки. Вердикты здоровья основаны только на наблюдаемом выводе CLI; портал, который не удалось протестировать, отчитывается как inconclusive, никогда не угадывается. Переключатель `enabled` - единственное, что проверка здоровья может менять, и только с подтверждением.
9. **Помечать паттерны распространения, никогда не обвинять.** Сигнал mass-posting (Step 2.5) описывает то, как распространяется листинг, а не заявление, что работодатель - мошенник. Никогда не называть компанию мошеннической или ненадёжной - представить наблюдение и дать пользователю решить самому.
