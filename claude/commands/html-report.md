# /html-report - Generate Application Tracker Dashboard

Сгенерировать самодостаточный HTML-дашборд из `job_search_tracker.csv` и архивов заявок в `documents/applications/`. Результат — один файл `.html` — без сервера, без зависимостей — открывается прямо в браузере.

## Step 0: Parse Arguments

- Без аргумента → вывод в `reports/application-dashboard.html`
- Аргумент-путь (например, `/html-report ~/Desktop/report.html`) → использовать этот путь
- Флаг `--open` → после записи сказать пользователю открыть файл (браузер напрямую открыть нельзя)

Создать `reports/`, если её нет.

---

## Step 1: Collect Data

Прочитать параллельно:

1. **`job_search_tracker.csv`** — основной источник. Разобрать каждую строку в запись с полями:
   `date`, `company`, `sector`, `role`, `role_type`, `channel`, `status`, `contact_person`, `fit_rating`, `notes`, `cv_file`, `cover_letter_file`, `source`, `deadline`

   Строки, записанные до появления `deadline`, несут тринадцать полей и без четырнадцатого значения. Считать отсутствующее поле пустым — никогда не отбрасывать строку и никогда не выводить дедлайн из её `date`.

2. **`documents/applications/*/outcome.md`** — по каждой закрытой заявке прочитать файл исхода, чтобы получить точные пройденные этапы интервью (чекбоксы) и заметки. Слить это с подходящей строкой трекера нечётким сопоставлением компания+роль (нижний регистр, без пунктуации). Если архив есть, а совпадения нет — всё равно прикрепить как дополнительный контекст.

Нормализация статуса — сопоставить значения трекера шести каноническим корзинам, прежде чем считать статистику:
- `drafted` → **Drafted** (документы написаны `/apply`, ещё не отправлены)
- `applied` → **Active** (резюме отправлено, дальнейшего сигнала нет)
- `interview` → **Interview**
- `offer` → **Offer**
- `hired` → **Hired**
- `rejected` / `no_response` / `no response` / `offer_declined` / `offer declined` / `withdrawn` → **Rejected/Closed**
- всё остальное → **Rejected/Closed**, отметить нераспознанное значение один раз в разбивке по статусам — сопоставление без учёта регистра

   Карта корзин на чтении терпит устаревшие написания через пробел, чтобы ничего, записанного до фиксации канонических форм, не выпало из статистики; **словарь статусов трекера** в `/outcome` — авторитетный набор.

## Step 2: Compute Summary Stats

Из нормализованных данных посчитать:

**Строки `drafted` исключены из каждой статистики ниже** — они никогда не отправлялись. Показать счётчик Drafted отдельно, включить его только в разбивку по статусам.

- **Всего заявок**
- **По корзине статуса:** счётчик по каждой корзине
- **По сектору:** счётчик по каждому уникальному значению сектора
- **По каналу:** портал vs. онлайн vs. referral vs. другое
- **По году/сезону:** группировка по полю `date` (может быть годом вроде `2025` или полной датой)
- **Funnel-конверсия:** какой % прошёл дальше скрининга резюме (дошёл до Interview или дальше). Вычислять достигнутый этап из истории, не из текущего статуса: заявка считается достигшей этапа, когда его подразумевает текущий статус **или** слитые чекбоксы этапов из `outcome.md` (Step 1.2) показывают, что этап пройден — строка `rejected`, чей файл исхода отмечает пройденный этап интервью, дошла до Interview, а строка `hired` прошла все этапы до Hired. Один только текущий статус структурно недосчитывает каждый более ранний этап: завершённый поиск читался бы так, будто никто никогда не проходил интервью.
- **Rejection rate:** реальные отказы (`rejected`, `no_response`) ÷ заявки с финальным исходом. `offer_declined` (кандидат сам отказался от оффера — это успех) и `withdrawn` (инициатива кандидата) не отказы и не входят в числитель; строки Interview и Offer ещё не разрешены, поэтому не входят в знаменатель, как и Active. Корзина статуса Rejected/Closed по-прежнему группирует все закрытые строки для doughnut-диаграммы — просто rate не должен слепо переиспользовать эту корзину.

## Step 3: Generate the HTML

Записать единый самодостаточный HTML-файл. Весь CSS инлайн в блоке `<style>`. Весь JS инлайн в блоке `<script>`. Рисовать doughnut- и bar-диаграммы как вручную сгенерированный инлайн SVG — никакого Chart.js, никакого CDN, никаких внешних зависимостей любого рода. Отчёт должен полностью рендериться офлайн при каждом открытии.

**Экранирование (обязательно):** HTML-экранировать каждое значение из CSV/файла исхода (`&` `<` `>` `"` `'`), прежде чем вставлять его в страницу — это касается ячеек таблицы, атрибутов `title` на усечённых заметках и любого текста внутри SVG (метки `<text>`, тултипы диаграмм). Заметки и названия компаний, скопированные из вакансий, регулярно содержат эти символы; неэкранированные, они ломают вёрстку или внедряют разметку в страницу, которую пользователь открывает регулярно.

### Design spec

- **Цветовая палитра:** CSS custom properties. Цвета статусов:
  - Drafted: `#64748b` (slate)
  - Active: `#3b82f6` (blue)
  - Interview: `#f59e0b` (amber)
  - Offer: `#8b5cf6` (purple)
  - Hired: `#22c55e` (green)
  - Rejected/Closed: `#ef4444` (red)
- **Шрифт:** стек system-ui, без веб-шрифтов
- **Карточки статистики:** белый фон, лёгкая тень, крупное жирное число, подпись под ним, левая граница цветом статуса
- **Диаграммы:** сетка в 2 колонки на широких экранах, друг под другом на узких
- **Таблица:**
  - Чередующаяся заливка строк
  - Колонка статуса — цветной pill/бейдж
  - Колонка `source` рендерится гиперссылкой, если значение — URL (начинается с `http`)
  - Пустые ячейки рендерятся как `—`
  - Клиентский фильтр: текстовый поиск фильтрует строки по компании + роли + сектору; выпадающие списки статуса и сектора фильтруют независимо; все три комбинируются (AND)
  - По умолчанию строки сортированы от новых к старым (по `date` по убыванию, затем по алфавиту компании)
- **Адаптивность:** пригодно от 900px, ниже не ломается
- **Футер:** «Generated by Claude Code · ai-job-search · {дата ISO}»

### Charts (inline SVG)

1. **Doughnut статусов** — сектор на каждую корзину статуса, цвета из палитры выше
2. **Bar по секторам** (горизонтальный) — количество компаний по сектору, по убыванию
3. **Bar по каналам** — онлайн / referral / другое
4. **Воронка заявок** (горизонтальный bar) — Applied → Interview → Offer → Hired, каждый бар = количество, дошедшее до этапа, выведенное по правилу воронки со Step 2 (текущий статус **плюс** слитые чекбоксы этапов из `outcome.md`), так что кандидат, прошедший интервью и позже получивший отказ, всё равно считается в баре Interview

Собирать каждую диаграмму как вручную написанный элемент `<svg>`: вычислять длины баров/углы дуг doughnut из статистики со Step 2 и выводить элементы `<rect>`/`<path>`/`<circle>` и `<text>` напрямую — никакой библиотеки диаграмм, никакого `<canvas>`. У каждого `<svg>` есть `role="img"` и `aria-label`, суммирующий диаграмму (например, «Разбивка по статусу: 3 Active, 2 Interview, 1 Offer»). Обернуть каждый в `<div class="chart-card">` с `<h3>`-заголовком сверху. Не забыть экранировать любой текст меток/значений, попадающий в узлы `<text>`, по правилу экранирования выше.

### Table: columns to include

`Дата` · `Дедлайн` · `Компания` · `Роль` · `Сектор` · `Канал` · `Статус` · `Заметки` (усечено до 80 символов, полный текст в `title`-тултипе) · `Источник` (ссылка или `—`)

Колонки, где во всех строках только пустые значения, можно опустить.

## Design Principles

- **Self-contained.** Один файл, полностью офлайн — диаграммы инлайн SVG, никакого CDN или внешних запросов любого рода.
- **Data-only.** Эта команда читает и рендерит; она никогда не пишет в трекер или архив.
- **Idempotent.** Повторный запуск перезаписывает предыдущий отчёт по тому же пути — без накопления.
- **Graceful on sparse data.** При всего нескольких строках (как сейчас) диаграммы корректно рендерятся для маленького N; таблица — основная ценность. Не скрывать диаграммы только потому, что N маленькое.
- **No fabrication.** Каждое число в отчёте берётся прямо из CSV или файлов исхода. Не выводить и не оценивать отсутствующие поля.
