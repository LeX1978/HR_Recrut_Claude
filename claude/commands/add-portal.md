# /add-portal - Generate a Job-Portal Search Skill for Your Local Market

Помощь пользователю в создании скилла поиска по площадке для его рынка. Репозиторий содержит готовые примеры паттерна (страно-агностичные `linkedin-search` и `freehire-search`, плюс `hh-search`, собранный для рынка РФ/СНГ этим же процессом) — эта команда превращает тот же паттерн в управляемый процесс: исследовать площадку, собрать скилл по канонической структуре и прогнать живой запрос, прежде чем что-либо регистрировать.

Генератор **страно-агностичен**: работает для любой площадки на любом рынке и языке. Скиллы, которые он производит, специфичны под рынок и живут в этом форке рядом с уже установленными.

`$ARGUMENTS` может содержать подкоманду, URL площадки, или ничего.

Шаги — **строго по порядку**.

---

## Step 0: Parse Arguments

- Если `$ARGUMENTS` содержит `--list`: через Glob по `.agents/skills/*/SKILL.md` напечатать таблицу установленных портальных скиллов (имя, рынок из описания, источник данных из `url-reference.md`), остановиться.
- Если `$ARGUMENTS` содержит URL: считать его URL площадки и передать на Step 1.
- Иначе: начать интервью со Step 1.

---

## Step 1: Interview - Portal Basics

Спросить у пользователя (пропустить то, на что уже ответил `$ARGUMENTS`):

1. **URL площадки** — публичный сайт борда вакансий (например, `https://hh.ru`, `https://career.habr.com`).
2. **Имя скилла** — kebab-case, с суффиксом `-search` (например, `geekjob-search`, `getmatch-search`). Не должно совпадать с уже существующей папкой в `.agents/skills/`.
3. **Рынок и язык** — какую страну/регион покрывает площадка и на каком языке её вакансии. Это определяет триггерные фразы в `SKILL.md` (включить термины на местном языке — так, как описание `hh-search` включает «вакансии», «поиск работы»).
4. **Реалистичный тестовый запрос** — название должности или навык, который пользователь реально бы искал, используется для живого теста на Step 4.

---

## Step 2: Investigate the Portal

Провести разведку, прежде чем писать код. Использовать WebFetch (или `curl` через Bash) по площадке:

1. **Найти паттерн URL поиска.** Загрузить страницу поиска площадки, мысленно или через fetch выполнить поиск и определить: эндпоинт поиска, параметр запроса, параметры локации, возраста вакансии и пагинации. Предпочесть JSON API, если он есть за сайтом (проверить на XHR-эндпоинты `/api/` в исходнике страницы); иначе готовиться разбирать HTML-страницу результатов.
2. **Получить один ответ поиска** по тестовому запросу и определить поля каждого результата: **id, название, компания, локация, дата публикации, URL**. Для HTML — отметить имена классов/атрибуты, на которых держится каждое поле. Для JSON — отметить пути полей.
3. **Найти паттерн страницы детали** — URL, возвращающий полное описание одной вакансии, и где в нём лежат описание, дедлайн, тип занятости и ссылка на отклик.
4. **Проверить требования доступа и условия использования.**
   - Получить `robots.txt` и проверить, не запрещены ли пути поиска/детали.
   - Если площадка требует логин/авторизацию для просмотра списков — **остановиться**: этот паттерн работает только на публичных страницах. Сказать пользователю и предложить проверить, нет ли у площадки официального API.
   - Если robots.txt запрещает пути, или условия площадки запрещают автоматический доступ — сказать об этом пользователю прямо и дать решить, продолжать ли для личного использования. При продолжении сгенерированный `SKILL.md` **обязан** нести заметное предупреждение «только для личного использования» (скопировать тон раздела «⚠️ Personal use only» у `linkedin-search`: держать объём низким, никакого коммерческого или массового использования, ответственность на пользователе).

5. **Проверить, доступна ли площадка без credential.** Некоторые площадки отдают пригодный контент только через сторонний сервис получения (платный unlocker/прокси API). **Этот пункт никогда не отменяет пункт 2.4:** если `robots.txt` или условия площадки запрещают доступ — решение принято там, и платный сервис получения этого не меняет. Путь с credential существует для площадок, чей `robots.txt` разрешает доступ, но чья защита от ботов блокирует обычные запросы. Где это применимо и тестовый запрос проходит только через такой сервис — сказать об этом пользователю **до сборки скилла** — площадка, берущая плату за запрос, это другое предложение, чем бесплатная, и пользователь может предпочесть её пропустить. Отметить, какой сервис и какая переменная окружения; правила обработки — в контракте портального скилла на Step 3.

Записать всё найденное — эндпоинты, параметры, якоря полей, особенности — это пойдёт в `url-reference.md` на Step 3.

---

## Step 3: Scaffold the Skill

**Канонический образец:** прочитать `.agents/skills/linkedin-search/`, прежде чем генерировать — это готовый пример этой самой структуры с нулевыми зависимостями. Копировать его архитектуру, не специфичный для LinkedIn парсинг.

Создать `.agents/skills/<name>/`:

```
<name>/
├── SKILL.md              # Определение скилла с триггерными фразами
├── url-reference.md      # Документация эндпоинтов со Step 2
└── cli/
    ├── package.json
    ├── tsconfig.json
    ├── README.md
    ├── src/
    │   ├── cli.ts        # Разбор аргументов, help, диспетчер команд
    │   ├── helpers.ts    # Fetch с backoff, парсеры, вывод ошибок
    │   └── commands/
    │       ├── search.ts
    │       └── detail.ts
    └── tests/
        └── helpers.ts    # утилиты runCLI + parseJSON для тестов (скопировать из linkedin-search)
```

### The portal-skill contract (every generated skill MUST honor this)

Эти конвенции делают портальные скиллы взаимозаменяемыми для `/scrape` и для пользователей, читающих документацию любого скилла:

- **Команды:** `search` и `detail <id|url>`.
- **Флаги поиска:** `--query`/`-q`, `--jobage <days>` (возраст вакансии; сопоставить с параметром площадки, отметить в SKILL.md, если не поддерживается), `--page <n>` (с 1), `--limit <n>` (ограничение на стороне клиента), `--format json|table|plain` (по умолчанию `json`). Добавить `--location`/`-l`, если площадка поддерживает локацию как параметр (`hh-search` поддерживает, с именованными РФ-регионами — см. его SKILL.md); если локация поддерживается только внутри поискового запроса — задокументировать это в SKILL.md нового скилла вместо флага («указывайте город в `--query`»).
- **Форма JSON-вывода:** `{ "meta": { "count": ..., "page": ... }, "results": [...] }`, где у каждого результата минимум `id`, `title`, `company`, `location`, `date`, `url` (отсутствующие значения — `null`, никогда не опускаются).
- **Ошибки:** пишутся в **stderr** как `{ "error": "...", "code": "..." }`, код выхода `1`. Никогда не писать ошибки в stdout.
- **Fetching:** честный User-Agent, называющий инструмент (`Mozilla/5.0 (compatible; <portal>-cli/1.0)`, конвенция каждого CLI в комплекте) — никогда не полная имитация браузера; если площадка отклоняет этот UA, эскалация к браузерным заголовкам идёт через robots.txt-гейт в `.claude/skills/job-application-assistant/09-web-research.md`, не через дефолт CLI. Экспоненциальный backoff с джиттером на 429/5xx (макс ~6 попыток), `""`/`null` на 404 вместо падения.
- **Разбор HTML:** делить ответ на чанки по результату и разбирать каждый независимо, чтобы одна битая карточка не сломала остальные (см. `parseJobCards` в `linkedin-search/cli/src/helpers.ts`).
- **Зависимости:** по умолчанию **нулевые зависимости в рантайме** (только `bun` + `fetch` + regex-парсинг), как `linkedin-search` — `bun install` должен подтягивать только dev-типы. Добавлять библиотеку парсинга, только если разметка площадки реально не поддаётся чанкованному regex-разбору, и отметить это в README.
- **Credentials:** скилл, которому нужен API-ключ (пункт 2.5), читает его **только** из переменной окружения `<SERVICE>_API_TOKEN`. Никогда не хардкодить, никогда не принимать как CLI-флаг (флаги утекают в историю шелла и список процессов), никогда не писать реальный токен в `url-reference.md`, пример в README или тестовую фикстуру. Если переменная не задана — выход с кодом `1`, стандартная JSON-ошибка в stderr и код `MISSING_CREDENTIALS`, с названием нужной переменной — никогда не проваливаться в неавторизованный запрос с непонятным падением. `.gitignore` репозитория уже покрывает `.env`; не коммитить его.

### File specifics

- **`SKILL.md` frontmatter:** `name`, `version: 1.0.0`, `description`, написанное для триггеринга скилла — должно называть площадку, рынок и включать триггерные фразы на английском **и** на языке рынка; `context: fork`; `allowed-tools: Bash(bun run skills/<name>/cli/src/cli.ts *)`.
- **`SKILL.md` body:** что скилл ищет, предупреждение о личном использовании, если Step 2 нашёл ограничения условий, справочник команд с флагами, 4-6 примеров использования под рынок пользователя (реальные города, реалистичные роли), таблица форматов вывода, раздел Notes с особенностями площадки со Step 2. Если Step 2.5 нашёл, что площадке нужен credential — добавить раздел **Setup**, называющий сервис, точную переменную окружения для экспорта и факт, что каждый запрос платный — сказано там, где пользователь это прочитает до запуска скилла, не после.
- **`url-reference.md`:** эндпоинты, таблица параметров и заметки о структуре ответа со Step 2 — этот файл понадобится будущему мейнтейнеру, когда площадка поменяет разметку.
- **`package.json`:** имя `<portal>-cli`, `"type": "module"`, скрипты `start`, `test` (`bun test --timeout 30000`) и `typecheck` (`tsc --noEmit`); dev-only зависимости при нулевых зависимостях по умолчанию.
- **`tests/`:** скопировать `runCLI`/`parseJSON` из `linkedin-search/cli/tests/helpers.ts`, затем добавить небольшой живой smoke-тест: `search` с тестовым запросом возвращает код выхода 0 и ≥1 результат с непустыми `id`/`title`/`url`; неверный флаг или отсутствующий обязательный аргумент завершается кодом 1 с JSON-ошибкой в stderr.

## Step 4: Test-Run a Live Query (MANDATORY)

Никогда не регистрировать портальный скилл, не вернувший реальные результаты. Предположения о разметке со Step 2 регулярно упускают особенности, видные только вживую.

1. Установить dev-типы и типизацию:
   ```bash
   cd .agents/skills/<name>/cli && bun install && bun run typecheck
   ```
2. Прогнать живой поиск с тестовым запросом пользователя:
   ```bash
   bun run src/cli.ts search -q "<тестовый запрос>" --limit 5 --format table
   ```
3. Проверить, что результаты реальны и полны: названия и компании заполнены (не пустые строки и не HTML-фрагменты), URL ведут на площадку, даты разбираются. Если поля приходят null или искажёнными — поправить парсеры в `helpers.ts` и перезапустить. Итерировать до чистого результата.
4. Взять один `id` из результатов и запустить `detail`:
   ```bash
   bun run src/cli.ts detail <id> --format plain
   ```
   Проверить, что описание — читаемый текст (сущности декодированы, теги убраны, разрывы абзацев сохранены).
5. Прогнать тесты: `bun run test`.
6. Держать объём низким во время итераций — горстка запросов, не краулинг. Если площадка ограничивает по частоте посреди теста — снизить темп и сказать пользователю.

К Step 5 не переходить, пока search, detail и тесты не пройдут.

## Step 5: Register

1. Спросить, хочет ли пользователь добавить новую площадку в стратегию поиска `/scrape`. При согласии:
   - CLI площадки уже подхватывается `/scrape` автоматически (он находит `.agents/skills/*/SKILL.md`) — дополнительной проводки для поиска/детали через CLI не нужно.
   - Опционально добавить placeholder-запросы WebSearch/`site:` для этой площадки в `.claude/skills/job-scraper/search-queries.md` (использовать уже имеющиеся там placeholder'ы вида `[YOUR_JOB_BOARD]`), чтобы фолбэк-путь всё равно покрывал площадку, если CLI недоступен.
2. Напомнить пользователю добавить строку установки для собственных записей, если он ведёт README форка:
   ```bash
   cd .agents/skills/<name>/cli && bun install && cd ../../../..
   ```
   (Пропустить, если скилл с нулевыми зависимостями и типы для typecheck не важны.)
3. Отметить, что скилл срабатывает автоматически по описанию в `SKILL.md` — другой проводки не нужно.
4. У этого форка нет CI-воркфлоу (пуш на удалённый репозиторий не настроен — коммиты остаются локальными сознательно, см. `project-context.md` в Obsidian-vault). Гонять `typecheck`/`test` для нового CLI вручную после каждой правки — так же, как это делал Step 4 выше.

## Design Principles

- Генератор страно-агностичен; его вывод специфичен под рынок.
- Разведка перед сборкой: команда никогда не генерирует парсеры по догадке — Step 2 сначала получает реальные ответы, Step 4 проверяет по живым данным, прежде чем что-либо регистрируется.
- Контракт портального скилла держит каждый сгенерированный скилл взаимозаменяемым с уже установленными: те же команды, те же флаги, та же форма вывода, та же конвенция ошибок.
- Нулевые зависимости в рантайме по умолчанию, как у `linkedin-search` — портальный скилл должен работать на свежем клоне без ничего, кроме `bun`.
- Правила доступа выносятся наружу, не обходятся молча: площадки за авторизацией отклоняются, ограничения robots.txt/условий использования сообщаются пользователю, ограниченные площадки получают заметное предупреждение «только для личного использования» в сгенерированном скилле.
- Credentials живут в окружении, никогда в репозитории: сгенерированный скилл читает токен из переменной окружения, громко падает, если она не задана, и никогда его не коммитит. Стоимость за запрос раскрывается до генерации скилла, не обнаруживается постфактум.
